# Luna: динамические субагенты, самообучающиеся профили и режим команды

Дата: 2026-11-16 · Ветка: `feat/dynamic-subagents-teams`

## Зачем

Сейчас субагенты задаются заранее: три встроенных (`researcher`, `reviewer`,
`general-purpose`) и профили из `subagents.toml`. Главный агент может выбрать
только имя (`subagent_type`) и написать задачу. Он не может:

- дать субагенту системный промпт под конкретную задачу;
- выдать нужный набор инструментов: `VALID_TOOLS` содержит 9 встроенных, а MCP,
  LSP и скилы субагенту недоступны;
- выбрать модель под задачу;
- продолжить работу уже запущенного субагента.

Пользователю нужны три вещи, по порядку:

1. **Динамические субагенты.** Главный агент сам собирает субагента под задачу:
   промпт, инструменты, скилы, модель.
2. **Самоулучшение.** Удачные сборки запоминаются. Периодический анализ находит
   повторяющиеся шаблоны и сам сохраняет их как профили, которые доступны в
   следующий раз.
3. **Режим команды (teams).** Автономная среда: дал задачу, ушёл, вернулся. Команда
   агентов выполнила её полностью или частично, и есть отчёт: что сделано, что нет,
   что пошло не так.

Решения сверены с аналогами: Goose `delegate`, Kimi CLI, Agent Zero, Codex
`spawn_agent`, OpenClaw, Claude Code agent teams, CrewAI, AutoGen/AG2, GitHub
Copilot coding agent, Codex exec, OpenHands headless.

**Критерий успеха.**

- Главный агент собирает субагента с собственным промптом, подмножеством своих
  инструментов (включая MCP/LSP), скилами и моделью, и может продолжить его работу
  по `resume`.
- Повторяющаяся удачная сборка (≥ 5 запусков, ≥ 70 % успешных) без участия человека
  становится профилем в `subagents.toml`. Это видно в `/subagents history`, и это
  можно откатить.
- `luna team "задача"` после одного подтверждения плана работает до конца без
  вопросов человеку:
  - рабочая копия пользователя и `main` не тронуты;
  - результат лежит в ветке `luna/team/<id>`, отчёт в `.luna/teams/<id>/report.md`;
  - запуск переживает перезапуск сервера.
- Весь набор тестов зелёный на трёх ОС и не ходит в сеть (`FakeProvider`).

**Вне рамок.**

- Десктоп-приложение. Протокол `/teams` описан независимо от клиента, первый
  клиент — TUI.
- Вложенные команды и субагенты глубже 1.
- Распределённый запуск на нескольких машинах.
- Веб-доска.

## Порядок реализации

Одна спецификация, три плана. Каждый план даёт рабочий, проверяемый результат.

| План | Что | Зависит от |
|---|---|---|
| 1 | Динамические субагенты и `resume` | — |
| 1b | Журнал сборок, анализ, автопрофили | 1 |
| 2 | Режим команды | 1 (сборка участников), 1b (анализ после запуска) |

## Часть 1. Динамические субагенты

### 1.1 Инструмент `task`

К схеме добавляются необязательные поля. Старые вызовы работают без изменений.

| Поле | Тип | Смысл |
|---|---|---|
| `description` | str | Задача (как сейчас) |
| `subagent_type` | str | Базовый профиль. По умолчанию `general-purpose`, если задан `prompt`, иначе обязателен |
| `prompt` | str | Системный промпт. Заменяет промпт профиля |
| `tools` | list[str] | Подмножество инструментов **родителя**, включая MCP и LSP |
| `skills` | list[str] | Имена установленных скилов. Их текст вставляется в системный промпт |
| `model` | str | ID из `[subagents].models` или имя роли (`fast`, `strong`, …) |
| `max_steps` | int | Не больше `[subagents].max_steps` |
| `context` | str | Факты от родителя (пути, решения), добавляются в системный промпт |
| `resume` | str | `session_id` прошлого запуска: продолжить его разговор |
| `background`, `isolation` | — | Как сейчас |

Правила сборки (`resolve_spec`):

1. Базой служит профиль `subagent_type`. Поля вызова переопределяют его. Сборка
   считается **динамической**, если задано хотя бы одно из полей `prompt`, `tools`,
   `skills`, `model`, `context`.
2. `tools` только сужает права. Можно выдать лишь инструменты родителя. Субагенту
   **никогда** не выдаются: `task`, `task_status`, `task_cancel`, `manage_mcp`,
   `manage_skills`, `save_skill`. Глубина — 1, как в Goose, Codex и OpenClaw.
3. Пишущие инструменты (`write_file`, `edit_file`, `delete`, `execute`, а также MCP с
   пометкой mutating) в динамической сборке разрешены только при
   `[subagents].allow_write = true`. Иначе вызов отклоняется с понятной ошибкой.
   Профили из файлов это ограничение не затрагивает (у них по-прежнему ключ `unsafe`).
4. Неизвестный инструмент, скил или модель — ошибка, которую видит родитель. Список
   допустимого есть в описании инструмента.
5. Политика, подтверждения, `/undo` и изоляция в worktree работают как сейчас.
   Сборка не может ослабить `permissions.toml`.

`resume`: сессия ищется среди дочерних сессий текущей сессии (`EventLog.children`).
Субагент продолжает тот же разговор с той же сборкой, новые поля игнорируются.
Чужие и несуществующие id дают ошибку.

### 1.2 Настройки

```toml
[subagents]
dynamic = true          # главный агент может собирать субагентов
allow_write = false     # потолок прав для динамических сборок
models = []             # пусто: только роли; иначе разрешённые ID моделей
max_steps = 30          # потолок max_steps у вызова
```

ID моделей живут только в конфиге и в `luna/config/providers.py`.

### 1.3 Изменения в `luna-core`

- `SubagentSpec` получает поля `skills: tuple[str, ...] = ()`, `context: str = ""`,
  `auto: bool = False`, `disabled: bool = False`, `version: int = 1`.
- `VALID_TOOLS` перестаёт быть закрытым списком для профилей. Имена проверяются по
  инструментам родителя при запуске; при загрузке TOML проверяется только формат.
- `SubagentRunner.run(...)` принимает `spec: SubagentSpec` вместо имени (имя
  остаётся для совместимости). Добавляется `resume: str | None`.
- `_drive` строит системный промпт так: промпт сборки, затем `context`, затем блоки
  скилов.
- `SubagentResult` получает `steps`, `cost`, `hit_max_steps`, `cancelled`. Эти поля
  нужны для части 1b.

### 1.4 Видимость

- TUI и REPL: в строке инструмента показываются имя сборки и пометка `dyn`, если
  сборка динамическая. Состав сборки выводится по раскрытию.
- `luna sessions` / сайдбар: дочерние сессии, как сейчас, с метаданными сборки в
  `meta`.

## Часть 1b. Журнал сборок и автопрофили

### 1b.1 Журнал

Новая таблица в `sessions.db`, модуль `luna_core.assemblies`:

```
subagent_runs(id, ts, workdir, parent_session, child_session,
              base_profile, dynamic, spec_json, task_head,
              ok, cancelled, hit_max_steps, steps, cost, profile_name NULL)
```

- `spec_json` хранит промпт, инструменты, скилы, модель и `context`. Всё это
  написал родитель. Вывод инструментов и ответы субагента туда **не** попадают.
- `task_head` — первые 200 символов задачи.
- **Успех** = `ok и не cancelled и не hit_max_steps`. Это грубая мера. Её
  ограничение честно указано в «Рисках».

### 1b.2 Анализ (`distill`)

Когда запускается:

- каждые 20 новых записей;
- раз в неделю при старте сервера;
- после каждого запуска команды;
- вручную: `luna subagents distill` / `/subagents distill`.

Как работает:

1. Записи без `profile_name`, сгруппированные по `workdir`. Последние 200 штук.
2. Один запрос к роли `fast` с потолком стоимости: «найди группы похожих сборок,
   для каждой предложи обобщённый профиль». Ответ — JSON.
3. Код проверяет каждого кандидата:
   - ≥ 5 запусков в группе и ≥ 70 % успешных;
   - инструменты существуют;
   - имя не совпадает с ручным профилем;
   - пишущие права не выше `allow_write`.
4. Прошедшие проверку сохраняются автоматически, с `auto = true` и `version = N`:
   - в пользовательский `subagents.toml`, если группа встречается в двух и более
     `workdir`;
   - иначе в `.luna/subagents.toml` проекта.

   Записи группы помечаются `profile_name`.
5. Пользователь получает уведомление: «Luna сохранила профиль `migration-writer`
   (6/8 успешно)».

Защита:

- **Ручные профили** (без `auto`) анализ никогда не меняет.
- **Автоотключение.** Если у auto-профиля из последних 10 запусков успешных меньше
  50 %, ставится `disabled = true` и приходит уведомление.
- **История.** Таблица `subagent_profile_versions` хранит каждое сохранение и
  изменение. Команды:
  - `luna subagents history`;
  - `luna subagents undo <name>`;
  - `luna subagents disable|enable <name>`;
  - `/subagents` в TUI/REPL.
- **Нагрузка.** Анализ — это один запрос за раз и не чаще одного раза в час
  (см. правило про ключи в «Рисках»).

## Часть 2. Режим команды

### 2.1 Запуск

- **CLI:** `luna team "задача" [--budget $] [--yes] [--sandbox docker] [--allow-sleep]`
- **TUI/REPL:** `/team задача`
- **Управление:** `luna team list|show <id>|resume <id>|cancel <id>`

Каждый запуск — это серверная сессия с `meta.kind = "team"`. CLI без TUI запускает
сервер (`ensure_running`) и печатает прогресс одной строкой.

Главный агент **не может** запустить команду, может только предложить `/team`.
За это отвечает настройка `[team].agent_can_start = false`.

### 2.2 План (одно подтверждение)

Лидер (роль `strong`) изучает репозиторий **только на чтение** и строит план:

- цель и критерии готовности;
- задачи T1…Tn с зависимостями и типом (`code` / `research`);
- состав: для каждого участника профиль или динамическая сборка (часть 1) и модель;
- профиль прав (см. 2.6);
- лимиты и оценка времени и стоимости.

Пользователь видит план. Варианты: «Запустить» / «Править» (редактирование
текстом, лидер перестраивает) / «Задать бюджет» / «Отмена». С `--yes` план
принимается без показа, с профилем прав по умолчанию.

### 2.3 Доска и сообщения

Состояние хранится в `sessions.db`: `team_runs`, `team_tasks`, `team_messages`,
`team_events`.

- Статусы задачи: `pending` → `in_progress` → `done` | `failed` | `blocked`.
- Участник берёт готовую к работе задачу (все зависимости `done`) атомарной
  операцией.
- Инструменты участника:
  - `board_list`, `board_claim`, `board_update(status, note)`;
  - `send_message(to, text)` — только конкретному участнику или лидеру;
  - `read_messages`.
- Инструменты лидера — те же плюс:
  - `board_add`, `board_split`;
  - `hire(spec)` (в пределах лимитов), `retire(member)`;
  - `reassign`;
  - `broadcast(text)` — сообщение всем отправляет **только лидер**.
- Лидер работает по событиям. Он просыпается, когда задача сменила статус, пришло
  сообщение, участник завершился или сработал детектор застоя. Постоянно в цикле
  он не крутится.

### 2.4 Задачи с кодом

- Перед стартом создаётся ветка `luna/team/<id>` от текущего `HEAD`.
- Рабочая копия пользователя не меняется.
- Каждый участник работает в своём worktree от вершины командной ветки.
  Используется существующий `create_worktree` / `finish_worktree`.
- Завершённая задача вливается в командную ветку **последовательно** (merge-lock).
  После каждого вливания запускается verify-команда, если она настроена.
  - Конфликт превращается в задачу «разрешить конфликт».
  - Красные тесты возвращают задачу в работу с выводом тестов.
- `main` и ветку пользователя команда никогда не трогает. Слияние делает человек,
  команда для этого есть в отчёте.

Задачи-исследования пишут заметки в `.luna/teams/<id>/notes/<task>.md`. Итоговый
текст лидер собирает в отчёте.

### 2.5 Лимиты

| Лимит | По умолчанию | Настройка |
|---|---|---|
| Одновременно работающих участников | 4 | `[team].max_concurrent` |
| Участников за запуск | 8 | `[team].max_members` |
| Глубина | 1 (участник не создаёт субагентов) | — |
| Шагов у участника / у лидера | 30 / 60 | `[team].member_steps`, `lead_steps` |
| Темп запросов | адаптивный, старт 30 rpm | `[team].rpm` |
| Бюджет | **нет** | `--budget`, `[team].budget` |
| Время | 2 ч, мягкая остановка | `--time`, `[team].wall_clock` |
| Сообщения | без счётчика; детектор застоя | — |

**Rate gate** (`luna_core.rategate`):

- общий для всего процесса сервера: все команды, субагенты и сессии;
- токен-бакет;
- при 429 соблюдает `Retry-After` и вдвое снижает темп;
- после 10 минут без ошибок плавно возвращает темп к заданному;
- текущий темп виден в статус-баре.

**Детектор застоя.** Если за 3 пробуждения лидера на доске ничего не изменилось,
лидер получает сигнал «прекратить обсуждение». Ещё 3 пробуждения без изменений
завершают запуск со статусом `stalled`.

**Мягкая остановка** (время или бюджет). Новые задачи не выдаются. Текущие
участники получают 1 шаг на сохранение работы. Затем пишется отчёт.

### 2.6 Права и автономия

- Во время запуска вопросов человеку нет. Профиль прав утверждается один раз, в плане.
- Профиль состоит из правил `allow` для инструментов и команд (`execute: uv run
  pytest*`, `execute: git *`, MCP-серверы и т. п.).
- Всё за пределами профиля автоматически получает `deny`. Отказ записывается в
  `team_events` и попадает в отчёт («⊘ tester: `curl …` — не в профиле»).
- Правила `deny` из `permissions.toml` действуют всегда и сильнее профиля.
- `--sandbox docker` запускает всю команду в контейнере (`DockerSandbox`). Сеть по
  умолчанию выключена, `[team].network_allow` задаёт allowlist.
- **Честно:** в локальном режиме сеть не изолируется. Профиль не даёт команд вроде
  `curl`, но процесс, например тест, может сам выйти в сеть. Об этом говорит
  предупреждение в плане.

### 2.7 Прерывания

- **Сон.** На время запуска система не засыпает: `caffeinate -i` на macOS,
  `SetThreadExecutionState` на Windows, `systemd-inhibit` на Linux, если есть.
  `--allow-sleep` отключает эту защиту.
- **Перезапуск сервера.** Запуски в статусе `running` продолжаются автоматически.
  Задачи `in_progress` без живого участника возвращаются в `pending`, а их worktree
  коммитятся и удаляются. В отчёт пишется «прервано в HH:MM, продолжено».
- **Отмена.** `luna team cancel <id>` / Esc в TUI отменяет запуск по той же схеме,
  что мягкая остановка.
- **Продолжение.** `luna team resume <id>` (кнопка «Доделать») продолжает
  завершённый или частичный запуск. Лидер получает отчёт и доску как контекст.

### 2.8 Отчёт

`.luna/teams/<id>/report.md`, а также `luna team show <id>` и модалка в TUI.

Содержание:

- итог: `ГОТОВО` | `ЧАСТИЧНО n/m` | `ОСТАНОВЛЕНО` (время/бюджет/отмена) |
  `ЗАСТОЙ` | `ОШИБКА`;
- по задачам: кто делал, результат, коммиты;
- что не сделано и почему;
- что пошло не так: отказы прав, падения тестов, конфликты, прерывания, ошибки
  провайдера;
- ключевые решения лидера;
- стоимость и время по участникам;
- ветка, `diff --stat`, команда слияния;
- изменения профилей субагентов (часть 1b).

По завершении приходит уведомление: тост в TUI и системное уведомление, если оно
настроено.

### 2.9 Протокол и сервер

В `docs/protocol.md` добавляется раздел `/teams`:

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/teams` | Создать запуск и начать планирование (`{task, budget?, sandbox?, yes?}`) |
| `GET` | `/teams` | Список запусков текущего каталога |
| `GET` | `/teams/{id}` | Доска, участники, лимиты, статус |
| `POST` | `/teams/{id}/plan` | Принять план (`{action: start\|edit\|cancel, text?, budget?}`) |
| `POST` | `/teams/{id}/cancel` | Отменить |
| `POST` | `/teams/{id}/resume` | Продолжить |
| `GET` | `/teams/{id}/events` | SSE-поток |
| `GET` | `/teams/{id}/report` | Отчёт (markdown + структура) |

Новые события:

- `team_plan`
- `team_task` — смена статуса задачи
- `team_member` — участник нанят, работает, завершён, сколько стоит
- `team_message`
- `team_denied`
- `team_rate` — текущий rpm
- `team_done`

Поток лидера и участников идёт через уже существующие события с полем `member`.

### 2.10 TUI

Согласовано по макету https://claude.ai/artifact/Y4XDkTPsoK42Kzm3LuvWBB.

- **Чат.** Агент может предложить `/team`. В левом сайдбаре появляется раздел
  «Команды».
- **План.** `ModalScreen`: цель, критерии, задачи, состав, права, лимиты, оценка.
  Кнопки: Запустить / Править / Задать бюджет / Отмена.
- **Экран команды** (`TeamScreen`):
  - слева — дерево команды;
  - в центре — доска из 4 колонок (Ждёт / В работе / Готово / Проблемы) и поток
    событий с вкладками лидер / участник / все;
  - справа — участники (шаги, стоимость) и сообщения;
  - статус-бар: `готово n/m · агенты · rpm · $ · время · ветка · сон отключён`;
  - клавиши: Tab, 1–5, M, S, Ctrl+B, Esc.
- **Адаптация по ширине.** Уже 140 колонок правая панель уходит под клавишу. Уже
  100 колонок доска сворачивается в одну колонку с переключением статусов.
- **Отчёт.** `ModalScreen`, клавиши D (diff, `diffview`), F (доделать), O (открыть
  `report.md`).

## Риски и честные ограничения

- **Правило про ключи** (CLAUDE.md, 2026-10-22). Команда — это та самая долгая
  автономная нагрузка, из-за которой провайдер однажды заблокировал аккаунт.
  Поэтому:
  - rate gate общий для процесса и включён всегда;
  - старт 30 rpm; поднять темп выше можно только явной настройкой `[team].rpm`;
  - в плане показываются темп и оценка числа запросов;
  - в тестах и CI реальные ключи не используются никогда.
- **Мера успеха** в 1b грубая. «Не упал и уложился в шаги» не значит «ответ был
  полезен». Сглаживают это пороги, автоотключение и откат. Позже можно добавить
  оценку от родителя.
- **Автосохранение пишущих профилей** выбрано пользователем осознанно. Потолок —
  `allow_write`, плюс правила `deny` всегда.
- **Изоляция сети локально** — см. 2.6. Полная изоляция только с `--sandbox docker`.
- **Стоимость без бюджета по умолчанию.** Это решение пользователя. Оценка и
  текущие `$` всегда видны, `--budget` есть.

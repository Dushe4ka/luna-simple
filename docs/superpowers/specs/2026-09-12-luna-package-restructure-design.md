# Luna package restructure — design

## Проблема

`luna/` — плоский пакет из 28 файлов верхнего уровня (плюс `luna/ui/`, уже
подпакет). После трёх релизов (0.2.0, 0.2.1, 0.3.0) стало непонятно, что к
чему относится без чтения содержимого каждого файла. Задача — реорганизовать
пакет в подпакеты по смыслу, без изменения поведения, и обновить документацию
(`AGENTS.md`), которая уже устарела после 0.3.0.

## Не в скоупе

- Любые изменения поведения. Это чистый рефакторинг путей импорта и
  расположения файлов — ни один тест не должен потребовать изменения своей
  логики, только своих импортов.
- Публичный API для внешних потребителей не рассматривается: `luna-simple` —
  приватный репозиторий, единственный потребитель пакета — сам CLI
  (`luna.cli:main`) и тестовый набор. Обратная совместимость импортов вида
  `from luna.undo import ...` для гипотетических внешних пользователей не
  сохраняется.
- `luna/ui/` не трогаем — уже корректно организован как подпакет.
- Изменение `pyproject.toml`'s `[project.scripts]` не требуется:
  `luna.cli:main` остаётся верным путём, `cli.py` остаётся на верхнем уровне
  пакета.

## Целевая структура

```
luna/
  __init__.py
  __main__.py
  cli.py                  # точка входа argparse — остаётся на верхнем уровне

  core/                   # рантайм агента: ровно те модули, что либо трогают
    __init__.py           # deepagents/langgraph напрямую, либо определяют,
    agent.py              # что агенту разрешено делать
    session.py
    persistence.py
    toolguard.py
    permissions.py

  repl/                   # интерактивный слой поверх core
    __init__.py
    commands.py           # диспетчер slash-команд, CommandContext
    setup_wizard.py       # мастер `luna setup`
    usercmd.py            # кастомные команды из .luna/commands/*.md

  config/                 # настройки, ключи, провайдеры, цены
    __init__.py
    config.py
    credentials.py
    providers.py
    prompts.py
    usage.py
    models.toml

  turn/                   # всё, что крутится вокруг одного хода
    __init__.py
    context.py            # @file + закреплённые файлы
    memory.py             # .luna/memory/*.md
    undo.py               # снапшоты (git-дерево + файловый журнал), /undo /redo /diff
    gitinfo.py
    fmt.py                # авто-форматирование после правок
    diagnose.py           # диагностика после правок
    verify.py             # verify-команда

  extensions/             # подключаемые возможности
    __init__.py
    subagents.py
    extension_tools.py    # manage_mcp / manage_skills
    mcp.py
    skills.py
    registry.py
    lspnav.py             # опционально, extra luna-simple[lsp]
    initgen.py            # `luna init` / `/init`

  ui/                     # без изменений
    ...
```

Итого: 5 новых подпакетов (`core`, `repl`, `config`, `turn`, `extensions`) по
3–7 файлов каждый, плюс существующий `ui/`, плюс 3 файла на верхнем уровне
(точки входа). Ни один подпакет не превращается в новую свалку: самый
крупный — 7 файлов, что уже осмысленно читается за один просмотр `ls`.

## Инвариант: framework-импорты

`AGENTS.md` фиксирует правило: импорты `deepagents` / `langgraph` /
`langchain_mcp_adapters` живут ровно в 4 модулях (плюс два задокументированных
исключения — `subagents.py`'s декларативные `SubAgent`, и `undo.py`'s
`undo()`/`redo()`, лениво импортирующие `langchain_core.messages` только
внутри этих двух функций).

После реструктуризации это правило формулируется как: framework-импорты живут
в `luna/core/{agent,session,persistence,toolguard}.py`, плюс исключения в
`luna/extensions/subagents.py` и `luna/turn/undo.py`. Сам факт, что 4 из 5
«ядровых» модулей (`agent`, `session`, `persistence`, `toolguard`) физически
лежат в одном `core/` — побочный полезный эффект структуры, не новое правило;
`permissions.py` в том же `core/` НЕ импортирует фреймворк и остаётся
framework-free — это отражено в обновлённой формулировке `AGENTS.md`, а не
скрывается за расположением в каталоге.

## Риски и как их закрывают

- **Забытая точка импорта.** Каждый файл `luna/*.py` и каждый `tests/test_*.py`
  потенциально содержит `from luna.X import ...` / `from luna import X` на
  перемещаемый модуль. План разбивает перенос на задачи по подпакетам, и после
  **каждой** задачи — полный `uv run pytest -q` + `uv run ruff check luna
  tests`. Пропущенный импорт даёт немедленный
  `ImportError`/`ModuleNotFoundError` при сборе тестов — не может остаться
  незамеченным до конца работы.

  Порядок задач определён реальным графом импортов (проверено `grep` по всей
  кодовой базе, не предположением): `config/`, `turn/`, `extensions/` не
  импортируют друг друга и не импортируют кандидатов в `core/`/`repl/` — идут
  первыми, в любом порядке. `repl/commands.py` импортирует из `config/`,
  `extensions/` (`subagents`) и `turn/` (`undo`, `verify`) на уровне модуля —
  идёт после них. `core/session.py` импортирует `repl/commands.py` **на
  уровне модуля** (`from luna.commands import HELP, CommandContext,
  dispatch`), а `repl/commands.py` — `core/session.py` только **лениво**,
  внутри функций (`# lazy: session imports commands`, уже существующий в коде
  разрыв цикла) — значит `core/` идёт последним, а не первым: на момент его
  переноса `repl/` уже существует по новому пути, и оба места ленивого
  импорта в `commands.py` (`_compact`, `_init`) заодно переписываются с
  `luna.session` на `luna.core.session`.
- **Циклический импорт.** Перестановка файлов в подпакеты не меняет реальный
  граф импортов (Python не заботится о «слоях» каталогов, только о фактических
  циклах на уровне модулей) — если цикла не было в плоской структуре, его не
  появится и в подпакетах, при условии что относительные/абсолютные пути
  импорта переписаны точно на новое расположение. Тем не менее каждая задача
  завершается реальным запуском (`import luna.cli` через `pytest`), что и есть
  окончательная проверка отсутствия цикла.
- **`pyproject.toml` / упаковка.** `[tool.hatch.build.targets.wheel]` уже
  использует `packages = ["luna"]` — hatchling подхватывает вложенные
  подпакеты автоматически, без перечисления. Дополнительно билд пакета
  (`uv build --wheel` + распаковка) — часть финальной задачи, чтобы подтвердить
  это на практике, а не на веру.
- **`__pycache__` мусор от старых путей.** После перемещения файлов старые
  `luna/__pycache__/*.pyc` могут указывать на несуществующие модули — не
  влияет на `pytest`/`ruff` (они не читают `.pyc` для этого), но задача
  очистки (`find luna -name __pycache__ -exec rm -rf {} +`) включена в
  финальный шаг для чистоты рабочего дерева перед коммитом.
- **`__init__.py` подпакетов — пустые или с ре-экспортом?** Пустые. Ни один
  существующий импорт в кодовой базе не использует форму `from luna import
  session` (все — `from luna.session import X` или `from luna import
  submodule_a, submodule_b`), так что публичного «фасада» пакета сохранять не
  требуется — но каждый импорт вида `from luna import diagnose, fmt, gitinfo,
  ...` (сейчас в `session.py`) переписывается на явный путь через новый
  подпакет (`from luna.turn import diagnose, fmt, gitinfo`), а не полагается
  на ре-экспорт в `__init__.py`, чтобы граф импортов оставался явным и не
  зависел от порядка инициализации подпакетов.

## Документация

`AGENTS.md`'s раздел «Структура» переписывается под новое дерево (список из
28 строк «файл — что делает» становится списком по подпакетам с тем же
уровнем детализации на файл). Раздел «Соглашения» про framework-импорты
обновляется под новые пути (`luna/core/...` вместо голых имён). `README.md` не
содержит прямых путей к внутренним модулям (проверено — только команды/флаги
пользователя), правок не требует. `CHANGELOG.md` получает одну запись в
`### Изменено` — реструктуризация пакета, без изменений поведения.

## Критерии готовности

- `uv run pytest -q` — тот же набор тестов (271), тот же результат (270
  passed, 1 skipped), без единого изменения тестовой логики — только путей
  импорта в тестовых файлах.
- `uv run ruff check luna tests` и `uv run ruff format --check .` — чисто.
- `uv build --wheel` собирается и содержит все подпакеты (проверка через
  распаковку wheel).
- `AGENTS.md` соответствует фактическому дереву `luna/`.
- Framework-импорты остаются ровно там же (4 core-модуля + 2 исключения),
  только с обновлёнными путями `luna/core/...`, `luna/extensions/...`,
  `luna/turn/...`.
